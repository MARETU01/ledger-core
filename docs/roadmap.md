# 架构演进路线

[返回项目首页](../README.md) · [当前架构](architecture.md)

本文记录面向资金账户与模拟交易业务的建设建议。领域模型、一致性与生产运行能力均需后续建设，已有共享客户端和 Flyway 迁移能力在相关条目中单独说明。具体模型、协议和技术选型需在实现前评审；完成标准用于指导验收，不代表已有测试或运行保证。

## 建设顺序

| 阶段 | 目标 | 主要交付 | 完成标准 |
| --- | --- | --- | --- |
| 1. 账户与账务基础 | 建立可验证的资金规则 | 开户、入账、余额与流水查询、幂等记录、数据库约束与迁移 | 重复请求不重复入账；并发更新符合余额规则；失败事务无部分写入；流水可核对 |
| 2. 交易资金闭环 | 连接订单状态与资金状态 | 下单、冻结、成交扣款、撤单解冻、流程恢复与对账 | 覆盖服务重启、调用超时、重复事件和乱序事件，未完成流程可以查询和恢复 |
| 3. 生产运行能力 | 建立访问控制、故障边界和发布保障 | 权限、流量预算、指标追踪、审计、持续集成、备份恢复 | 关键操作可追溯；故障有告警和处理步骤；发布兼容性及恢复演练有记录 |

测试、数据库变更记录和请求标识应随第一阶段建立，后续阶段持续完善。服务进一步拆分应依据领域归属、容量、团队职责和故障隔离需求决定。

## 领域职责与数据归属

建议先沿用现有两个业务服务：

| 服务 | 建议拥有的数据与规则 | 对其他服务提供的能力 |
| --- | --- | --- |
| 账户服务 | 账户状态、余额、冻结记录、账务分录及流水 | 入账、冻结、确认扣款、解冻、查询执行结果 |
| 交易服务 | 委托、成交、撤单、订单状态及资金操作引用 | 下单、撤单、订单与成交查询 |

账户服务统一校验资金变化，交易服务保存关联资金操作的业务标识，通过账户接口或明确的事件协议交互。每类数据只有一个负责写入的服务，禁止跨 schema 直接更新。

建模前需要明确币种、金额精度及舍入规则、余额与冻结的关系、透支策略、流水核对方式，以及是否采用复式记账。每个操作都应定义允许的前置状态和合法状态迁移。上述决策通过后再建立表结构和 RPC。

## 本地事务、幂等与可靠消息

| 场景 | 建议约束 | 验证重点 |
| --- | --- | --- |
| 重复资金请求 | 明确幂等键的作用域和保存期限；数据库唯一约束；记录请求摘要及执行结果 | 同键同参数返回已有结果；同键不同参数明确拒绝 |
| 并发冻结或扣款 | 使用带条件的原子更新或明确的锁策略；受影响行数参与业务判断 | 不突破可用余额等业务约束；余额、冻结和流水原子提交 |
| 数据库提交后消息未发出 | 需要可靠事件时，在同一本地事务内写业务数据和 Outbox，再由投递任务发送 | 提交后宕机仍能恢复投递；投递失败有重试和积压告警 |
| 消息重复与乱序 | 消费去重记录与业务更新置于同一本地事务；检查状态与业务版本 | 重复事件无额外资金效果；乱序事件可拒绝、等待或进入人工处理 |
| 请求超时或断网 | 保留稳定业务标识并提供结果查询；定义未知结果的处理流程 | 客户端重试或查询后可以确认原操作结果 |

Kafka 生产者幂等只覆盖其协议层行为。Outbox 投递仍可能重复，消费方必须处理重复；数据库事务不会自动涵盖 RPC 或消息发送。

## 跨服务流程恢复

以“提交订单并冻结资金”为例，建议先记录可恢复的订单意图及资金操作标识，再调用账户冻结；成功后推进订单状态。具体中间状态和转换条件需与业务模型一起确定。

| 故障位置 | 需要明确的恢复行为 |
| --- | --- |
| 订单意图保存后，尚未调用冻结 | 恢复任务依据记录继续处理，或按业务期限关闭流程 |
| 冻结已成功，响应丢失 | 使用原操作标识查询或幂等重试，确认结果后推进订单 |
| 冻结成功，订单后续失败 | 使用关联冻结记录发起可幂等执行的解冻，并追踪补偿结果 |
| 成交与撤单并发 | 通过状态机和数据库并发控制判定合法转换，防止重复扣款或释放 |
| 恢复多次失败 | 形成告警和待处理记录，保留订单、资金操作和事件的关联信息 |

补偿本身也可能超时或失败，需要持久状态、重试和人工处理入口。定时对账应检查长时间未结束的冻结、订单与资金状态不一致，以及余额与账务记录不一致的情况。

## 接口与依赖治理

- 对外接口与内部 RPC 分开组织 protobuf service；当前网关对已配置 service 的全部 unary 方法开放 POST，新增方法时必须检查暴露范围。
- 为每次下游调用设置 deadline，确认调用取消与超时的传播；为下游调用、数据库访问及后台任务设置并发和排队上限。
- 仅对明确可重试的操作和错误设置有限重试；资金写入需先具备稳定幂等语义和结果查询。当前网关与 Java 示例未实现业务自动重试。
- 共享 gRPC 客户端已具备调用时的失效地址淘汰与有界关闭；后续验证真实 Nacos 实例上下线、地址变化及滚动停机，按需要增加后台发现刷新。
- 新增协议字段保持兼容，删除字段保留编号和名称；滚动发布期间验证新旧服务与网关协议缓存共存。

限流、熔断和隔离参数应来自压测及业务目标。虚拟线程、连接池大小和实例数量需要与数据库及下游的容量共同评估。

## 身份、数据与审计

入口需要校验用户或调用方身份，业务服务校验账户归属与操作权限，内部调用建立服务身份及传输保护。固定 API token 和调用者自报的用户标识不能承担完整权限校验。

数据库先为各服务配置独立角色及 schema 权限，再根据容量和故障隔离需求评估独立实例。应用运行角色与数据库迁移角色的权限应分开管理。

资金审计应关联操作者、业务请求、订单、资金操作及流水。明确可修改字段、历史记录保留方式和审计访问权限，避免日志记录凭据或完整敏感请求。

## 运行、交付与验证

| 范围 | 建议交付 | 验收证据 |
| --- | --- | --- |
| 可观测性 | 跨网关及 Java 服务的追踪；请求耗时、错误率、连接池、Outbox 积压、消费延迟与对账指标 | 故障可定位到调用或业务操作，关键积压与不一致有告警 |
| 健康与依赖 | 分别定义进程存活、接流量条件和依赖状态 | 下游故障时的健康检查行为及流量处理经过验证 |
| 数据库迁移 | 已有各服务独立的 Flyway 版本化脚本和历史表；后续完善兼容变更与发布顺序 | 应用新旧版本共存期间可运行，执行失败有处理方案 |
| 持续集成 | Java 与 Go 独立构建；规则、数据库并发、RPC 和事件集成测试 | 关键资金不变量和已知故障场景可自动验证 |
| 发布 | 配置与协议变更评审、逐步放量、停机排空及回退步骤 | 应用回退与数据库前向修复策略明确，发布演练有记录 |
| 恢复 | 明确可接受的数据损失范围和恢复时长；数据库备份及消息恢复方案 | 在隔离环境完成恢复演练，并校验账务及未完成流程 |

每阶段记录实际验证结果及未覆盖场景。当前可运行的构建与网关测试命令见[开发与排错](development.md)，HTTP 调用示例见[网关指南](../gateway/README.md#启动与验证)。
